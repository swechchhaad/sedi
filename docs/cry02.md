# SEDI-CRY-02: holder key control, migration and compromise

**Tool:** ProVerif 2.05. Trace properties use correspondence, secrecy and reachability queries; the PRV-01 cross-check uses observational equivalence.
**Model generator and runner:** [`scripts/cry02_proverif.py`](../scripts/cry02_proverif.py)
**Generated models:** [`proverif/cry02/`](../proverif/cry02/)
**Raw output, with traces:** `results/cry02/<config>.log`

```
python3 scripts/cry02_proverif.py          # generate + run all 17 configurations (~2 s)
python3 scripts/cry02_proverif.py --list
```

**Result:** all 127 results match the expected outcome: 120 query results across the 10 trace configurations (12 queries each), plus 7 equivalence checks. None are inconclusive (no "cannot be proved"). Every `false` result comes with a reconstructed ProVerif trace.

## 1. What CRY-02 requires, and what a symbolic model can show

| CRY-02 requirement | How it is treated here |
|---|---|
| 1. holder-controlled key generation | Keys are created with `new` **inside the holder's device process**. Neither the issuer nor any server takes part. |
| 2. non-extractability during normal operation | **Assumed, not proved (HW-NX).** A key that is never output is trivially secret in a symbolic model. We therefore state non-extractability as an explicit hardware assumption and **test what breaks when it fails** (configurations `E_*`). |
| 3. proof of key control without revealing the secret | Challenge–response: the verifier sends a fresh nonce and the device signs it. Queries Q1 and Q2. |
| 4. migration without credential reissuance | KERI pre-rotation: the AID is rotated to a pre-committed key held by the new device. Query Q4. |
| 5. no issuer/server copy of the private key | Query Q3, plus an escrow configuration where this is deliberately violated. |

**HW-NX (hardware assumption).** A device key is a `new` name, used only through `sign()`, and output only by an explicit compromise branch that raises a `Reveal` event. That the key stays inside the device is an assumption about the secure element. **The model does not show that CRY-02's non-extractability is satisfied.** It shows which of the other properties survive or fail when the assumption is broken in each of the ways listed in variant E.

**keripy today.** keripy's keystore ([`src/keri/app/keeping.py`](../src/keripy/src/keri/app/keeping.py)) holds private keys in an LMDB database, encrypted at rest (`pris.` via `CryptSignerSuber`). Keys are created either randomly (`RandyCreator`) or derived from a salt (`SaltyCreator`), and a salt-derived key can be regenerated by anyone holding the salt. So HW-NX is **not** provided by keripy itself. It has to come from the deployment: a secure element, a hardware-backed keystore, or edge signing.

## 2. Model
There are two phases:
- **phase 0:** before migration
- **phase 1:** after migration

### Parties
- **Old device:** generates the current key `sk0`. It incepts the holder AID `aid = h(pk(sk0), h(pk(sk1)))`, which commits to the next key in advance (pre-rotation). It then enrolls the AID with the issuer and answers verifier challenges. At migration it hands the new device the **AID and the credential, not any private key**.
- **New device / recovery hardware:** generates the pre-rotated key `sk1` at the start and sends only its digest to the old device. At migration it publishes a rotation event signed with `sk1`, commits to a fresh next key `sk2`, and from then on answers challenges with `sk1`.
- **Issuer:** issues **exactly one** credential, in phase 0, to the enrolled subject.
- **Witnesses (honest):** accept an inception only if the AID matches its keys. They accept a rotation only if the new key matches the pre-committed digest and the event is signed with that key. Only the first rotation seen is accepted. After recording a rotation they raise `MigrationDone`.
- **Verifier:** checks the issuer's signature on the credential, sends a fresh nonce, and verifies the response against its view of the holder's current key:
  - the inception key before migration;
  - the rotated key after migration;
  - a **stale** verifier still uses the inception key after migration.

### The two credential bindings (variant B)
| | The credential's subject is | Migration |
|---|---|---|
| `BIND_AID` (KERI/ACDC) | the holder AID | rotate the AID's keys; the credential is unchanged |
| `BIND_KEY` (device-bound, e.g. an mdoc-style device key) | the device public key `pk(sk0)` | the new device has a new key, so the credential no longer matches it |

## 3. Queries (lemmas)

| ID | Property | ProVerif query |
|---|---|---|
| sanity | a verifier can accept before migration (the model isn't dead) | reachability of `AcceptControl` |
| Q1 pre | **holder control:** an accepted proof means the device signed *that* challenge (injective) | `inj-event(AcceptControl) ==> inj-event(DeviceSigned)` |
| Q1 post | holder control after a completed migration | `AcceptCurrent ∧ MigrationDone ==> DeviceSigned` |
| Q1 pre/post \| comp | the same, **except** when the accepted key was compromised | `... ==> DeviceSigned ∨ Compromised(p)` |
| Q2 sk_old / sk_new | **key secrecy** | `not attacker(sk0)`, `not attacker(sk1)` |
| Q2 unless-reveal | the attacker knows a holder key only if a `Reveal` of that key occurred | `KeyGen(k) ∧ attacker(k) ==> Reveal(pk(k))` |
| Q3 | **no issuer/server copy** | `ServerGotKey` never happens |
| Q4 new-key accept | **migration:** the credential is accepted under the *new* key | reachability of `AcceptCurrent ∧ NewKey` |
| Q4 no reissue | ...and it is the credential issued once, in phase 0 (there is no other `Issued` event) | `AcceptCurrent(s) ==> Issued(s)` |
| Q5 | **old-key invalidation:** after a completed migration, no presentation under the old key is accepted | `AcceptCurrent(p) ∧ OldKey(p) ∧ MigrationDone ==> false` |

The sanity query holds in every configuration.

### Reading the table
- **Variants A–D, KERI with no compromise:** every property holds. The holder generates its own keys and proves control with a challenge–response, without the key leaving the device. No server gets a copy. The credential survives migration to a new device **without reissuance**, and after migration the old key is useless.
- **Variant B, device-key binding:** everything holds *except migration*. The new device cannot present the old credential (Q4 fails, proved by ProVerif), so the credential must be reissued. This is the concrete reason CRY-02 requirement 4 favours an AID/commitment binding over a raw device key.

## 5. Compromise boundaries (requirement 6)

| Compromise | Still holds | Fails | Why |
|---|---|---|---|
| **Signing-oracle access** to the current device (malware can make it sign, but can't read the key) | key secrecy (Q2); control after migration (Q1 post); old-key invalidation (Q5) | **control before migration (Q1 pre)** | The oracle can answer a verifier's challenge. Not revealing the key doesn't help, because proof of control *is* a signature. Migration restores control: the oracle only has `sk0`, and rotation needs `sk1`. |
| **Full extraction of the current key** | control after migration (Q1 post); old-key invalidation (Q5); secrecy of the next key | control before migration (Q1 pre); secrecy of `sk0` (Q2) | This is KERI pre-rotation working as intended: the attacker has `sk0` but cannot produce the rotation, because that needs the pre-committed `sk1`. The holder recovers by rotating. |
| **Old device compromised after migration** | every control and invalidation property | secrecy of `sk0` only (expected) | After rotation the old key is no longer current, so a verifier with **up-to-date key state** rejects it. |
| ...with a **stale verifier** | control before migration | **Q1 post, Q5**; Q4 (the new key isn't recognized) | The old key is accepted again. Old-key invalidation is only as good as the verifier's key-state freshness, which is the CRY-01 offline/online question. |
| ...with **device-key binding** | control before migration | **Q1 post, Q5**, Q4 | Nothing ever retires the old key, so a stolen old device keeps working until the credential is revoked. |
| **Pre-rotation (recovery) key compromised** before migration | control before migration; old-key invalidation | **control after migration (Q1 post)**; secrecy of `sk1` | The attacker can produce the rotation, or sign as the rotated key, so migration hands control to the attacker. In the model the attacker may also be the first to rotate (first-seen). This is the **one key compromise KERI cannot recover from** by rotation. The pre-rotated key must be protected at least as well as the current key. |
| **Issuer/server escrow** (server honest) | all control and secrecy properties | **no server copy (Q3)** | Violates CRY-02 requirement 5 by design, even if nothing leaks. |
| ...escrow **breached** | old-key invalidation only | Q3; Q1 pre and post; secrecy of both keys | An escrow of both keys is a single point of total compromise. Neither migration nor pre-rotation helps. |

Across all configurations, the "except after compromise" forms of Q1 hold. **A verifier accepts a proof of control only if the legitimate device signed it, or the accepted key was compromised.** There is no other way to fake control. Q2 unless-reveal also always holds: every key the attacker learns traces back to an explicit compromise.

## 6. Does binding the credential to a stable holder AID violate PRV-01?
The two-world observational-equivalence experiment is the same as in [`docs/prv01.md`](prv01.md). The credential copies have per-copy SAIDs, so only the AID/key binding can link presentations.

| Configuration | Unlinkable? | Distinguishing test (ProVerif) |
|---|---|---|
| one stable holder AID | **no** | `aid₁ = aid₂` |
| one stable holder AID, presentation 2 after key rotation | **no** | `aid₁ = aid₂`: rotation changes keys, **not the AID** |
| copies bound to one device public key | **no** | `pk(k₁) = pk(k₂)` |
| per-copy AIDs, but one device key signs for all | **no** | `pk(k₁) = pk(k₂)` (the current key in each inception event) |
| per-copy AIDs, but one pre-rotated (new-device/recovery) key for all | **no** | `h(pk(nx₁)) = h(pk(nx₂))`: the **next-key digest** in each inception event |
| per-copy AIDs with per-copy current and next keys | **yes** | none |
| per-copy AIDs, each rotated to its own new key | **yes** | none |

**Yes: a stable holder AID violates PRV-01.** This is the direct conflict between the two requirements:
- **CRY-02 migration relies on a stable AID.** The credential stays valid because the AID doesn't change when keys rotate.
- **PRV-01 is broken by that same stable AID,** even across rotations.

The way to satisfy both is **per-copy AIDs, each with its own current *and* pre-rotated key**. This is keripy's independent-AID bulk-issuance variant, extended to the next keys. The last row shows this survives migration. The cost is that migration means rotating **every** per-copy AID, M rotations for M copies, and the new device or recovery hardware must hold M pre-rotated keys. A single shared recovery key re-links every copy through the next-key digest, **before any migration happens**.

## 7. Limitations
- **Non-extractability is assumed (HW-NX), not proved.** Physical and side-channel extraction, secure-element attestation, and the correctness of a platform keystore are outside the model. The `E_*` configurations only model the *consequences* of the assumption failing.
- **One rotation.** A single migration is modeled. After a recovery-key compromise, the attacker's own next-key commitment would give it permanent control over further rotations. That takeover isn't modeled beyond the first rotation.
- **The verifier's key-state view is a parameter.** Each phase is given its view explicitly (inception key before, rotated key after, stale = inception key after), rather than looking up "the latest key". ProVerif over-approximates negative table lookups (`get ... else`); with that encoding, old-key invalidation came back "cannot be proved" with no attack trace. How a verifier gets fresh key state (carried KEL, cache, witness query) is analyzed in CRY-01.
- **Honest witnesses; first-seen rotation.** Witness duplicity and KAWA thresholds are not modeled. First-seen is written with `get ... else`, which ProVerif over-approximates (it may admit two competing rotations). That is sound, and it's why the recovery-key case assumes the attacker may win the race.
- **No delegation, no interaction events, no revocation (TEL) in this model.** A stolen old device under device-key binding is only stopped by revocation, which isn't modeled here.
- **Symbolic cryptography:** perfect signatures and hashes; no key-size or algorithm-agility questions.
